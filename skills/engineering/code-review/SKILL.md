# Code Review

对当前 diff（或 PR / 分支）做双轴审查：
1. **规范符合**：代码是否实现了 spec / ticket 描述的行为
2. **工程标准**：代码质量、测试质量、架构合理性

## 何时运行

- **服务器端**：`/integrate` 合并完成后，运行一次快速 review，确认集成结果合理
- **本机端**：拉取服务器结果后，运行正式 review，作为交付前的最终检查

## 流程

### 1. 确定审查范围

读取当前 diff：
- 如果在 ticket 分支上：diff = 该分支相对于其 base 分支的变更
- 如果在 integration/main 上：diff = 相对于 main 的全部变更
- 也可以指定 PR 号或分支名

### 2. 规范符合审查

逐个检查 spec / ticket 中的验收标准：
- [ ] 验收标准 1 是否被实现
- [ ] 验收标准 2 是否被实现
- ...

对每个验收标准，指出代码中实现它的位置（文件 + 行号）。如果找不到实现，标记为 missing。

### 3. 工程标准审查

检查以下方面：

- **测试**：是否在 ticket 指定的 seam 上测试？测试是否只测外部行为？有无实现耦合或同义反复反模式？
- **架构**：变更是否引入了不必要的耦合？是否有更深的模块可以拆出？
- **命名**：变量、函数、文件命名是否与项目术语一致？
- **边界**：错误处理、空值处理、边界条件是否覆盖？
- **安全**：如果涉及认证、加密、权限，是否有明显漏洞？

### 4. 输出审查报告

```markdown
## Code Review 报告

### 规范符合
- [x] 验收标准 1：[文件:行] 实现正确
- [ ] 验收标准 2：未找到实现，missing

### 工程标准
#### 测试
- seam：[文件] 测试在正确 seam 上
- 反模式：无
#### 架构
- 评价：变更合理，未引入不必要耦合
#### 命名
- 术语一致性：符合 CONTEXT.md 术语表
#### 边界
- 空值处理：<评价>

### 发现
1. [严重] <描述> → <建议>
2. [建议] <描述> → <建议>
3. [通过] 无问题

### 结论
- [ ] 可合并
- [ ] 需修复后合并
- [ ] 需重新实现
```

## 审查原则

- **假设善意**：代码是 agent 写的，agent 不是故意写烂代码，先理解它为什么这么写
- **追溯 intent**：如果代码看起来奇怪，追溯 ticket 的任务描述理解 agent 的 intent
- **不追求完美**：追求"够好"，不追求"完美"。如果代码实现了 spec、测试通过、架构不恶化，就是可接受的
