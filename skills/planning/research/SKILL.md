# Research

在规划过程中，你会遇到需要查文档、读源码、验证 API 行为才能回答的问题。这些是**事实型问题**，不该拿去问用户。用本 skill 派一个后台 agent 去查。

## 定位

本机规划端的辅助 skill。它在 `/grill-me` 进行中或 `/to-spec` 之前被调用：当发现某个技术问题阻塞了规划推进时，暂停规划，先调研，拿到结果后继续。

调研文档只有一个成功标准：**你读完三十秒内能拍板**。做不到就是材料不够，不是文档不够长。

## 流程

1. **明确调研问题**：用一句话表述要回答的核心问题。如果问题太大，拆成几个子问题。

   问题要写成能被否定的形式。「OAuth 怎么做」不能拍板；「access token 过期后，前端该自动刷新还是引导重新登录」能拍板。

2. **启动后台 agent**：使用 Agent 工具，类型选 `general-purpose` 或 `Explore`，把调研任务派出去。

   Agent 的 prompt 模板：
   ```
   调研问题：<核心问题>

   要求：
   - 查阅 primary source（官方文档、源码、API spec），不要引用二手文章
   - 每个结论附来源，并写明依据在来源的哪一节、哪个文件、哪一行
   - 查证过程单独成节，用三列表格记「预想 / 让它站不住的材料 / 现在的写法」，
     不要把这个过程写成结论里的铺垫，那是翻案腔，见 /readable-docs
   - 结论如果不确定，写清不确定到什么程度，以及可以用什么方法验证
   - 输出为单个 Markdown 文件
   - 文件路径：.workflow/research/<topic-slug>.md
   - 遵守 /readable-docs：数不出材料的段落直接删掉，不要为了对齐模板灌水
   - 章节标题带 emoji 帮人扫读，自己按内容选，不要套固定模子
   - 涉及三个以上组件、有状态迁移或失败路径时，画一张 Mermaid 图，节点用代码里的真实名字
   ```

   如果这次是**补全已有文档**（同一个问题第二次调研），在 prompt 里明确写上路径和这条要求：新材料写进对应的节，不要追加在末尾，不要留「补充」「更新」这类痕迹。

3. **继续手头工作**：agent 在后台跑，你可以继续 grill-me 的其它轮次。agent 完成后会通知。

4. **整合结果**：读取调研文档，把结论整合进规划上下文。

   读的时候如果发现自己要重新推理一遍才能得出结论，说明文档没写到位，退回让 agent 重写对应段落。这比你自己补一轮推理便宜。

   如果是补全流程，另检查一遍文档有没有留痕：翻到末尾看看有没有冒出一节「补充说明」，通读一遍看有没有「之前提到……现在更正」这类句子。留痕的文档下次再补就没人能读了。

## 调研文档格式

结构用下面这个，每一节写成什么样按 `/readable-docs` 执行。模板是骨架，不是要写满的格子。

标题上的 emoji 只是示意，你按这份调研的内容自己选一套，同一份文档里保持一致。

`/readable-docs` 有完整规则。有两条执行时最容易打折扣，这里点出来：

- ✂️ **段落要短。** 一段一个意思，讲完就空行换段，三五行为宜，不要出现大段文字
- 🎨 **emoji 不要省。** 每个段落开头、每个列表项都配一个做锚点，密度高一点比密度低一点好读

```markdown
# <调研主题>

## 🎯 问题
<核心问题的一句话表述，可以被回答成是或否、选 A 或选 B>

## ✅ 结论
<第一句直接给判断，是可以拿去拍板的说法。不要用「经过调研」「主流做法是」开头。
 后面每段给一条支撑理由，理由带具体依据：文档章节号、源码行号、实测数字。
 最后一段落到本项目的实际后果：要改什么、要加什么、要付什么代价。>

<结论涉及三四个以上组件、或者有状态迁移和失败路径的，这里放一张 Mermaid 图。
 图的画法见 /readable-docs 的「Mermaid 图」一节：一张图一个主题，
 节点用代码里的真实名字，边上写清流过去的是什么。>

## 📚 依据
- [来源](url) <章节号>：<这份来源具体说了什么，哪句话支持了上面的哪条结论>
- <源码路径:行号>：<这段代码实际做了什么>

## 🔬 查证过程
<三列表格，每行一条被推翻或修正的预想：预想 / 让它站不住的材料 / 现在的写法。
 只记材料怎么改变了判断，不加「但是」「其实」这类转折词，
 也不要写成「我一开始不懂」这类自白。写法见 /readable-docs 的「查证过程 vs 翻案腔」。
 查证过程另有价值，它让读者判断这条结论查得够不够，不要省略。>

## ⏳ 不确定的部分
<写清不确定的程度和验证方式，不能只写「需要进一步调研」。
 例：官方文档没有对这个行为的明确描述，只在 GitHub issue #123 里有人提到，未本地复现。
 可以用 <具体命令> 在十分钟内验证。>

## 🚧 范围外
<有明确不回答的问题时才写这一节，没有就删掉。
 范围外和不确定是两回事：不确定是我查了但没查实，范围外是这件事本次就不打算回答。
 两者搅在一起，读者会分不清哪些是材料不够、哪些是你划的边界。>

## 🧭 对我们的影响
<这份结论改变了哪个决定，或者确认了原本的哪个方案。
 有 follow up 动作（改代码、加测试、调整 ticket 拆分）就写在这里。>
```

### 节的集合

上面六节是默认骨架，其中「不确定的部分」和「对我们的影响」每份都要有，其余按材料决定。判断标准是那一节里有没有其它节装不下的新东西。常见的加节情形：

- 结论里的「实际后果」分成两截时，拆成两节：机制层面的代价（要改配置、要付性能开销、有反直觉的取舍）和本项目层面的影响（改变哪个决定、有什么 follow up）。堆在一节里读者分不清哪句是对系统说的、哪句是对我们说的
- 结论依赖某个版本门限、配置约束或环境前提时单开一节，不要把这些塞进结论的段落，它们会淹没判断本身
- 有明确不回答的问题时加「范围外」。声明边界本身就是信息，但它不属于「不确定」

不要为了对称加节，也不要删节。删掉「不确定的部分」是最常见的错误，那份文档会显得比实际更可靠。

## 补全：分几次查完时怎么办

调研经常不是一次查完的。第一次没查到的东西，第二次查到了，这时候最容易出问题。

**把新材料写进正文对应的节，不要贴在文末。** 具体做法：

- 新事实属于「结论」就改「结论」，属于「依据」就加进「依据」
- 新事实推翻了旧结论，就改掉那一句，不要保留旧版加一条更正
- 不要出现 `## 补充`、`## 更新记录`、`## 勘误`、`## 附录` 这类标题
- 不要写「补充一点」「之前提到 X，现在更正为 Y」
- 不要用 emoji 标出哪些是新增的

判据是一个没读过旧版本的读者能不能直接拿到当前答案。不能就是留痕了，重写。

变更过程记在 git commit 里。`/readable-docs` 的「补全与返工」一节有完整规则和对照样例。

如果第二次查到的是一个**新问题**，按「一个问题一个文件」另建文件，在原文件的相关位置加一行链接指向它。

## 路径

调研文档存入 `.workflow/research/`。文件名用 kebab-case 主题 slug，如 `oauth-token-refresh.md`。

## 规则

- **primary source only**：官方文档、源码、spec、第一方 API。不引用博客、教程、二手文章。
- **一条结论一个来源**：每个结论都追溯到具体的 URL 加章节，或文件加行号。
- **不确定就说**：查不到就写「未能在 primary source 中确认」，并写清不确定的程度和验证方法，不要推测。
- **一个问题一个文件**：不要把多个不相关的问题塞进一个调研文档。
- **写不长就写短**：结论三行也行。为填满模板而灌水比文档太短更糟。

## 下一步

调研完成后把结论带回 `/grill-me` 或 `/to-spec`，不要单独交一份文档就结束。

## 回报给用户

按 `/readable-docs` 的「写完之后的回复」发一条四块回复：产出路径与状态、结论一句话、需要用户知道的、下一步。

调研类的第二块重点是**结论和不确定在哪**，第三块给结论引出的选型取舍。最多五条，超过就指路不复制。未验证的部分、规则没覆盖的地方必须写出来。
